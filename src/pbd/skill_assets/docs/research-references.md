# Research references and adoption decisions

Reviewed 2026-11-24. These are references for original PBD guidance, not copied implementations or claims of standards compliance. Market tools are covered in [market research](market-research.md).

| Source | Design application |
|---|---|
| [Bill Wake, user stories and SMART tasks](https://xp123.com/user-stories/) and [Agile Alliance INVEST](https://agilealliance.org/glossary/invest/) | story quality, task decomposition; not a score or fixed sizing rule |
| [Agile Alliance Three Cs](https://agilealliance.org/glossary/three-cs/) | conversation and confirmation; record questions rather than invent outcomes |
| [Scrum Guide](https://scrumguides.org/scrum-guide.html) | progressive refinement, developer sizing, DoD and roles; no required story syntax |
| [Humanizing Work story splitting](https://www.humanizingwork.com/the-humanizing-work-guide-to-splitting-user-stories/) | vertical slices and adaptive splitting |
| [Agile Alliance story mapping](https://agilealliance.org/glossary/story-mapping/) | journey backbone and usable release slices |
| [Lucassen et al., Improving agile requirements: the Quality User Story framework and tool](https://doi.org/10.1007/s00766-016-0250-x) | QUS/AQUSA; hybrid review; measure false positives and negatives rather than treating lexical heuristics as proof |
| [Cucumber Example Mapping](https://cucumber.io/docs/bdd/example-mapping/) | story/rule/example/question separation |
| [Cucumber Gherkin reference](https://cucumber.io/docs/gherkin/reference/) and [better Gherkin](https://cucumber.io/docs/bdd/better-gherkin/) | context/event/outcome, domain-level examples |
| [Alistair Mavin, EARS](https://alistairmavin.com/ears/) | structured requirement patterns, optional format |
| [NASA requirement-writing checklist](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/) | clear verifiable constraints; adapt to context rather than applying aerospace policy wholesale |
| [IREB glossary](https://cpre.ireb.org/en/downloads-and-resources/glossary) | requirements vocabulary and validation vs verification |
| [Microsoft Azure Boards backlog](https://learn.microsoft.com/en-us/azure/devops/boards/backlogs/create-your-backlog?view=azure-devops) and [processes](https://learn.microsoft.com/en-us/azure/devops/boards/work-items/guidance/choose-process?view=azure-devops) | native acceptance fields, process-specific types and rules |
| [Brazilian Digital Government User Story](https://www.gov.br/governodigital/pt-br/estrategias-e-governanca-digital/startupgovbr/guia-gps/pages/5-saiba-mais/praticas-de-engenharia-de-software/user-story/) | pt-BR terminology and INVEST |

No benchmark executed in this research round. Standards ISO/IEC/IEEE 29148 and ISO/IEC 25010 are conceptual references, not claimed conformance. Validate licensing before reuse of external code or text.
