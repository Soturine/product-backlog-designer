# Methodology

## Source intelligence
Inventory the entire allowed scope before extracting. One semantic reader per declared source, not a fixed agent count. Directory sources inventory every authorized member; bounded chunks and resumable checkpoints for large inputs. Read tables, footnotes, diagrams, errors, exclusions, revisions and acceptance criteria. Unreadable evidence blocks completeness assertions. No programmatic keyword-only extraction or generation in place of actual semantic analysis.

## Authority
Functional authority defines intended behavior; technical authority constrains implementation; approved decisions supersede only explicitly affected claims; existing backlog and code are evidence, not automatic authority. Log disagreements and ask focused questions with impacts and alternatives. Do not treat suggestions as confirmed requirements.

## Planning
Extract atomic obligations independently of work-item count; classify functional, nonfunctional, integration, operational, security, data, accessibility, error and out-of-scope claims. Build actors and state transitions. Epic = outcome; Feature = capability; Story = valuable vertical slice; acceptance = observable condition; Task = concrete work with expected output and verification. Add technical discovery/spikes when evidence insufficient. No fixed number of Stories, Tasks or criteria. Use INVEST, 3Cs, SMART where useful, EARS, Gherkin/BDD, Story Mapping and SPIDR where appropriate. Use MoSCoW, WSJF or RICE only with inputs and explicit scales. DoR/DoD are team policies, not interchangeable with acceptance. Reference ISO/IEC/IEEE 29148 and ISO/IEC 25010 conceptually; no compliance certification claimed. Scrum estimates are developer-owned; AI proposals are not official.

## Traceability and audit
Every obligation gets COVERED, PARTIALLY_COVERED, NOT_COVERED, QUESTION_REQUIRED, CONFLICTING, OUT_OF_SCOPE, SUPERSEDED or DEFERRED. Justify all dispositions with locators. Reverse check every work item, acceptance criterion and task against source or explicitly proposed technical rationale. Review every item individually, not merely aggregate findings. Separate confirmed divergence, ambiguous source, unsupported assumption, planning gap and optional improvement. Report what source asks, what backlog says, why different, impact, recommended change, decision needed and affected IDs. Independently re-read original sources before scoring; record omissions discovered. Semantic equivalence may be many-to-many.

## Change management
Compare versions, classify added/removed/changed obligations, map affected items, preserve identity and human edits, require approval for scope removal. Never equate title changes with new identity. Plan dependencies and sprints only after validating constraints; no fictitious capacity or deadlines. FTD must independently read functional authority.
