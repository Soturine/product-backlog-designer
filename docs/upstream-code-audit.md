## Concrete source findings

- Azure Prototype `format_devops_description` (lines 130–165) puts criteria and task list in the description, with interpolated strings. PBD needs native Acceptance Criteria field, structured children and explicit HTML sanitization.
- Its `_push_devops_work_item` (289–363) calls CLI create, then separate parent linking; `_link_parent` (364 onward) does not check nonzero exit from subprocess. In this inspected path a failed link can leave a returned created ID without confirmed hierarchy. Test creation/link failures, verify final state; do not copy as-is. The inspected path also derives area from epic text; discover actual area instead.
- Its `BacklogState.set_items` resets push status arrays by list position (74–112). PBD should bind journal to stable IDs, target and operation hash, not array index. Resume and reconcile ambiguous outcomes.
- PRD to Jira `load_epics` (28–46) rejects unknown dependency IDs: the current inspected implementation DOES perform that check, correcting earlier broad characterization. It does not in that function detect duplicate IDs/cycles. CSV writer uses epic summary links, default priority and locale-dependent file encoding. PBD must add schema, uniqueness, cycles, UTF-8 and injection safety. This is a finding about those functions, not the complete project.
- FTD's validation gate builder returns PASS for gates after the pipeline is expected to enforce them; PBD must bind each gate to actual recorded validation, not mechanically call a pass builder. FTD's emitted-field hash is an excellent synchronization primitive to generalize.
- Assertiva's gate evaluator distinguishes executed vs imported evidence and empty runs. PBD must likewise separate "audit completed", "coverage verified" and "ready to publish"; mandatory PBD gates cannot pass simply because nothing was examined.
- OpenSpec's validator validates a parsed model using Zod and accumulates structured errors, including failures reading/parsing. PBD should distinguish unreadable source vs absent requirement and use pre-write checks.
- HVE's core includes partial autonomy for low-risk updates; PBD uses explicit approval for all remote writes. Its reference has quality at four levels: adapt level-specific review, no duplicate parent acceptance criteria or fixed quotas.

## Implementation order and reuse gate

M0: pin exact upstream commits and per-file licenses; define adapter seams, canonical schemas, source registry, run manifest and gate evidence. Prefer standard library or small original primitives. M1: candidate generic FTD state/validation/render logic plus Assertiva presentation helpers, original PBD data model and semantic playbooks. M2: adapt HVE/Spec Kit/PM review patterns, add independent source coverage. M3: generic FTD auth/transport/approval primitives, Azure API contracts, original Boards field mapper, guarded CLI launcher. M4: HVE capacity ideas; M5: OpenSpec delta and journal ideas. Keep third-party runtime dependency optional unless its value is demonstrated.

For each copied or adapted file require an adoption record: upstream URL and commit/blob, license/notice, purpose, modifications, dependency surface, security review, original and new tests, behavior difference, update policy. If a license is uncertain, use conceptual inspiration only. No bulk merging unrelated repositories. Benchmark reuse versus original implementation on correctness, maintainability, latency, dependency footprint and UX before claiming improvement.
